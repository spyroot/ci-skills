# CI05-VENDOR: vendored `glab` skills and upstream references, one lock

Status: proposed. Order and dependencies: CI10-PHASES, Phases.

## Goal

Copy the agent skills that the GitLab CLI (`glab`) ships into
`vendor/skills/<name>/` (planned, CI05-VENDOR), so this repository owns them,
lists them (CI01-CATALOG) and routes to them (CI08-ROUTING), and detect any
later drift or hand edit. The same declarations, lock and transaction serve
the upstream references that CI09-REFERENCE vendors into
`ci-skills/references/vendor/<name>/` (planned, CI09-REFERENCE): one
`vendor/vendor.toml`, one `vendor/vendor.lock.json` and one
`tools/skillkit/transaction.py` (all planned, CI05-VENDOR).

## What glab ships

`glab skills list`, observed with glab 1.120.0 on 2026-10-02, reports three
skills. Its own help marks the `glab skills` command as an experiment, and it
has no JSON output.

| Skill | Source | Upstream project | License |
| --- | --- | --- | --- |
| `glab` | bundled | `gitlab-org/cli` | MIT |
| `glab-stack` | bundled | `gitlab-org/cli` | MIT |
| `orbit` | remote | `gitlab-org/orbit/knowledge-graph` | undecided |

- The `glab` skill names its upstream in its frontmatter
  (`metadata.source-project`). `glab-stack` names none; it ships in the same
  binary, which is built from `gitlab-org/cli`.
- MIT requires its notice in every copy: "Copyright (c) 2022-present GitLab
  Inc." and "Copyright (c) 2019 GitHub Inc.".
- `orbit` declares `license: MIT` in its frontmatter, but its source project
  carries the GitLab Enterprise Edition license at its root and has no
  license file under `skills/orbit`. That license requires its full text in
  every copy, so `orbit` stays out until the open decision below is made.

## Layout

```text
vendor/skills/glab/SKILL.md              upstream bytes
vendor/skills/glab/LICENSE               MIT notice, added here
vendor/skills/glab-stack/SKILL.md        upstream bytes
vendor/skills/glab-stack/LICENSE         MIT notice, added here
ci-skills/references/vendor/<name>/      upstream reference trees (CI09-REFERENCE)
vendor/vendor.toml                       declared by hand
vendor/vendor.lock.json                  generated by update, one lock for every tree
```

Each vendored skill carries its own `LICENSE`, because CI01-CATALOG installs
one skill at a time; a single shared notice would not travel with it.

## Declarations and lock

**`vendor/vendor.toml`** is edited by hand and validated against
`vendor-declarations` (CI07-SCHEMA). It declares:

- **The skills to fetch.** Each skill's name and source (`glab-bundled` or
  `glab-remote`). `update` fetches only declared names, so nothing depends on
  parsing the human-readable output of `glab skills list`.
- **Per skill:** its `tags`, `license` and `notice`, the name of the notice
  file. Upstream frontmatter for `glab` and `glab-stack` has no tags, so this
  file is their one declaration.
- **Fetch settings:** `attempts` and `backoff_seconds`.
- **References**, each as a `[references.<name>]` table that CI09-REFERENCE
  owns, together with the `vendor-declarations` MINOR bump it needs
  (CI07-SCHEMA, Versions).

The notice text comes from the `LICENSE` of the upstream release that built
the installed `glab`. It is added once, by hand, and `update` keeps it.

**`vendor/vendor.lock.json`** is written only by `update`, never by hand,
and validated against `vendor-lock` (CI07-SCHEMA). It is the one lock for
every vendored tree: CI09-REFERENCE adds its `references` entries beside
`skills`, with the same per-file and tree digests.

```json
{
  "schema_version": "1.0",
  "kind": "skill_vendor_lock",
  "skills": {
    "glab": {
      "source": "glab-bundled",
      "fetched_with": "glab 1.120.0",
      "upstream": {
        "project": "gitlab-org/cli",
        "path": "internal/commands/skills/bundled/assets/glab"
      },
      "files": {
        "LICENSE": {"sha256": "...", "origin": "local"},
        "SKILL.md": {"sha256": "...", "origin": "upstream"}
      },
      "tree": {
        "algorithm": "sha256-tree-v1",
        "digest": "...",
        "file_count": 2
      }
    }
  }
}
```

Where each lock field comes from:

- **`source`:** the declaration in `vendor/vendor.toml`.
- **`fetched_with`:** `glab --version`, read when `update` runs.
- **`upstream.project` and `upstream.path`:** the skill's frontmatter
  `metadata`, or `null` where it names none. `glab-stack` names neither.
- **`files`:** the SHA-256 of each file in the set that `tree_digest` covers
  (`_included` in `ci-skills/lib/core/provenance.py`, which this phase makes
  public as `included_files` beside `file_digest`, step 2), computed by `tools/skillkit/vendor.py` through that module.
  `origin` is `upstream` for fetched files and `local` for the notice.
- **`tree`:** `tree_digest` from that same `provenance.py`, the digest the
  installer and the live acceptance check already use.

## Interface

```text
bin/ci-skills verify [--receipt-out PATH] [--json | --yaml | --human]
bin/ci-skills update [NAME ...] [--apply --confirm-plan DIGEST] [--json | --yaml | --human]
```

Exit codes, the result envelope and `safe_next_step` follow CI02-CLI.
The maintenance verbs apply only with `--apply --confirm-plan DIGEST`, the
digest of the plan the default run printed, as the skill actions do
(CI02-CLI, item 6; D-CONFIRM). `--receipt-out` is the
receipt option every smoke case runs with (CI06-TESTS, Live smoke), which
`access_check.py` already has; this phase adds it to `verify`. Each reason
token below is defined once, in `tools/skillkit/vendor.py`, with its safe
next step:

| Token | Meaning |
| --- | --- |
| `lock_unreadable` | the lock is missing or not valid JSON |
| `file_missing` | a file the lock lists is absent, the notice included |
| `digest_mismatch` | a file or the tree differs from the lock |
| `unexpected_file` | the skill holds a file the lock does not list |
| `symlink_unexpected` | a symbolic link in a staged or committed tree |
| `glab_unavailable` | `update` cannot run `glab` |
| `skill_unknown` | the name is not declared in `vendor/vendor.toml` |
| `fetch_failed` | the fetch failed on every configured attempt |

- **`verify`** needs no `glab`, no network and no third-party package.
  `bin/ci-skills` imports PyYAML only for `list` and `--yaml`; `verify`
  checks hashes only and stays on the standard library, and full schema
  validation is the `schemas` gate's job (CI07-SCHEMA, Validation). `verify`
  refuses symbolic links itself: `tree_digest` skips them, so a matching lock
  alone does not prove a tree is safe. Gap: whether `verify` also walks the
  lock's `references` entries, and where the hash walk it shares with
  CI09-REFERENCE's `bin/reference.py verify` lives so that it is not a second
  implementation, is CI09-REFERENCE's to define.
- **`update` plans by default** (CI02-CLI). It lists, per skill, the files
  that would be added, changed or removed, and writes only with
  `--apply --confirm-plan DIGEST` (CI02-CLI, item 6).
- **A fetch heals before it blocks.** `update` retries `attempts` times,
  waiting `backoff_seconds` between tries, then reports `fetch_failed` with
  each attempt's error.
- **Only `update` calls `glab skills`.** If that experimental command changes
  or disappears, `verify` and the vendored copies keep working.

## Update transaction

`update --apply` changes several files at once, one tree per skill plus
the lock. The steps are the ones `tools/skillkit/transaction.py` provides,
journal, lock, stage, swap, read-back and recover, extracted from
`tools/install_ci_skills.py`: `plan_fingerprint`, `_journal_path`,
`_mutation_lock`, `_write_journal`, `_recoverable_signals`, `_read_journal`,
`_recover_install_unlocked`, `recover_install`, and the staging, rename and
read-back block inside `_install_unlocked`. The installer then calls them;
`_install_unlocked` and `install` themselves stay there until CI01-CATALOG,
Steps, moves them to `tools/skillkit/install.py`. CI09-REFERENCE runs the
same transaction for a reference tree, so there is one implementation.

1. Write a transaction marker (the installer's journal) beside the staging
   directory, recording the skills and the backup paths.
2. Fetch every named skill into the staging directory with
   `glab skills install <name> --path <staging>`.
3. Check each staged tree: its frontmatter `name` equals its directory name,
   it holds no symbolic link, and its declared notice is present.
4. Write the new lock to a temporary file beside the current one.
5. For each skill, rename the current tree to a backup, then rename the
   staged tree into place.
6. Rename the temporary lock over the current lock.
7. Run `verify`. On success, delete the backups and the marker. On any
   handled failure, restore every backup and the previous lock, then delete
   the marker.

If the process is killed partway, the marker survives. The next `update` or
`verify` finds it, restores the backups and the previous lock first, and
reports that it recovered.

## Code placement

- **`bin/ci-skills`** is created by this phase: the repository's maintenance
  command, a thin main like `bin/ci-api`, with `--help` and `--describe`
  (CI02-CLI, Steps). Its logic is Python in `tools/skillkit/` (planned,
  CI05-VENDOR): `vendor.py` and `transaction.py` here. CI01-CATALOG extends
  the command with `list`, `get` and `install`; CI09-REFERENCE reuses the
  transaction and the lock.
- **`tools/skillkit/` imports `core` from `ci-skills/lib`** (CI10-PHASES,
  Layout, decided), one import direction: `skillkit` imports
  `core.provenance`, as the installer does, and computes the per-file hashes
  through it. Never the reverse: an installed skill ships without `tools/`,
  and editing `provenance.py` would change the skill digest.

## Steps

How we consume the skills that the installed `glab` ships:

1. Amend `environment.yml`: add `-r requirements.txt` to its pip section
   (Python 3.11 is pinned there already), and create or refresh the
   `ci-skills` conda environment from it before anything runs.
2. Build `tools/skillkit/transaction.py` (extracted from
   `tools/install_ci_skills.py`, which then calls it),
   `tools/skillkit/vendor.py` and `bin/ci-skills` with its `verify` and
   `update` verbs, `--help` and `--describe`; write the tests of "Delivery,
   test and proof" with the block. In `ci-skills/lib/core/provenance.py`,
   make `included_files` and `file_digest` public and add the `excluded`
   parameter and `VENDOR_DIRECTORIES` (D-DIGEST).
3. Declare `glab` and `glab-stack` in `vendor/vendor.toml`, add each notice
   from the upstream release's `LICENSE`, and add the `vendor-declarations`,
   `vendor-lock`, `skill_vendor_check` and `skill_vendor_update` schemas at
   `0.<minor>` (CI07-SCHEMA, Steps and Versions).
4. Run `bin/ci-skills update glab glab-stack` to see the plan, then run it
   again with `--apply --confirm-plan DIGEST`, which performs the update
   transaction.
5. Run `bin/ci-skills verify`; it must report `PASS`.
6. Add the `.markdownlint-cli2.yaml` ignores and the unconditional `verify`
   gate (CI03-GATES, G4).
7. Open one pull request; merge per CI10-PHASES, How a phase lands.

Steps 4 and 5 are also the refresh path: `update` shows upstream drift,
`update --apply --confirm-plan DIGEST` applies it, and the diff goes through a pull request.

## Gates

- **CI.** `bin/ci-skills verify` runs unconditionally (CI03-GATES, G4).
- **Markdown lint.** Vendored text stays byte-for-byte upstream. Measured
  with markdownlint-cli2 0.23.2, `glab` has 2 and `glab-stack` 30
  line-length findings (MD013). This phase adds `vendor/skills/glab/**` and
  `vendor/skills/glab-stack/**` to the `ignores` of the committed
  `.markdownlint-cli2.yaml`, which every markdownlint run reads.
- **Measured on the fetched copies.** No trailing whitespace, CRLF or tabs,
  so `git diff --check` passes; no gitleaks finding; no project-neutrality
  violation.
- **Tests.** Written with the block; run status UNVERIFIED (CI03-GATES, G0).
  The pytest and bats suites are never run on this laptop.
- **Receipt.** The vendored trees do not move the executed-code digest:
  `vendor/` is outside the skill, and `ci-skills/references/vendor/**` is
  excluded by D-DIGEST. This phase's code does move it: the
  `core/provenance.py` change (step 2) and the `verify` gate in
  `ci-skills/lib/bash/ci/check.bash` (step 6) are bytes inside `ci-skills/`,
  so the receipts are recaptured on the D-SMOKE executor after the last edit
  (CI03-GATES, G5). A receipt applies until it expires (`captured_at` plus
  `max_receipt_age_days`; CI03-GATES, G7). As read back on 2026-10-06, the
  committed receipts already mismatch the skill digest (CI10-PHASES, Pull
  request status); whether that blocks a merge is D-GATE (CI03-GATES, G0).
