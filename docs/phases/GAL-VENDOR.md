# GAL-VENDOR: vendored glab agent skills

Status: proposed. Depends on: nothing. Followed by: GAL-CATALOG.

## Goal

Copy the agent skills that the GitLab CLI (`glab`) ships into `skills/`, so
this repository owns them, lists them (GAL-CATALOG) and routes to them
(GAL-ROUTING), and detect any later drift or hand edit.

## What glab ships

`glab skills list`, observed with glab 1.120.0 on 2026-10-02, reports three
skills. Its own help marks the `glab skills` command as an experiment.

| Skill | Source | Upstream project | License |
| --- | --- | --- | --- |
| `glab` | bundled | `gitlab-org/cli` | MIT |
| `glab-stack` | bundled | `gitlab-org/cli` | MIT |
| `orbit` | remote | `gitlab-org/orbit/knowledge-graph` | undecided |

- The `glab` skill names its upstream in its frontmatter
  (`metadata.source-project`). `glab-stack` names none; it ships in the
  same binary, which is built from `gitlab-org/cli`.
- MIT requires its notice in every copy: "Copyright (c) 2022-present GitLab
  Inc." and "Copyright (c) 2019 GitHub Inc.".
- `orbit` declares `license: MIT` in its frontmatter, but its source project
  carries the GitLab Enterprise Edition license at its root and no license
  file under `skills/orbit`. That license requires its full text in every
  copy, so `orbit` stays out until the open decision below is made.

## Block

| Part | Value |
| --- | --- |
| Capability | copy, record and verify vendored skills |
| Owner | `tools/skillkit/vendor.py` |
| Entrypoint | `tools/ci_skills.py verify` and `update` |
| Result | `skill_vendor_check`, `skill_vendor_update` |
| Read-back | `update` runs `verify` after it writes |

## Layout

```text
skills/glab/SKILL.md          upstream bytes
skills/glab/LICENSE           MIT notice, added here
skills/glab-stack/SKILL.md    upstream bytes
skills/glab-stack/LICENSE     MIT notice, added here
skills/vendor.toml            declared by hand: tags, license, notice
skills/vendor.lock.json       generated by update: what was copied
```

Each vendored skill carries its own `LICENSE` because GAL-CATALOG installs
one skill at a time; a single shared notice would not travel with it.

## Declarations and lock

- `skills/vendor.toml` is edited by hand. Per skill it declares `tags`,
  `license` and `notice`, the name of the notice file. It also holds the
  fetch settings `attempts` and `backoff_seconds`. Upstream frontmatter for
  `glab` and `glab-stack` carries no tags, so this file is their one
  declaration.
- The notice text comes from the `LICENSE` of the upstream release that
  built the installed `glab`. It is added once, by hand, and `update` keeps
  it.
- `skills/vendor.lock.json` is written only by `update` and never by hand.

```json
{
  "schema_version": "1.0",
  "kind": "skill_vendor_lock",
  "skills": {
    "glab": {
      "source": "glab-bundled",
      "fetched_with": "glab 1.120.0",
      "upstream": {
        "project": "gitlab-org/cli",
        "path": "internal/commands/skills/bundled/assets/glab"
      },
      "files": {
        "LICENSE": {"sha256": "...", "origin": "local"},
        "SKILL.md": {"sha256": "...", "origin": "upstream"}
      },
      "tree": {
        "algorithm": "sha256-tree-v1",
        "digest": "...",
        "file_count": 2
      }
    }
  }
}
```

Where each lock field comes from:

- `source`: `glab-` plus the Source column of `glab skills list`, so
  `glab-bundled` or `glab-remote`. GAL-CATALOG adds `local` for skills that
  live here.
- `fetched_with`: `glab --version`, read when `update` runs.
- `upstream.project` and `upstream.path`: the skill's frontmatter
  `metadata`, or `null` where it names none (`glab-stack` names neither).
- `files`: the SHA-256 of each file in the set that `tree_digest` covers
  (`_included` in the k8s skill's `scripts/core/provenance.py`), computed in
  `tools/skillkit/vendor.py`. `origin` is `upstream` for fetched files and
  `local` for the notice.
- `tree`: `tree_digest` from that same `provenance.py`, the digest the
  installer and the live acceptance check already use.

## Interface

```text
tools/ci_skills.py verify [--json | --yaml]
tools/ci_skills.py update [NAME ...] [--dry-run] [--json | --yaml]
```

Exit 0 means `PASS` or `DRY_RUN` and 2 means anything else, as defined by
the k8s skill's `scripts/core/status.py`. Reason tokens are defined once, in
`tools/skillkit/vendor.py`:

| Token | Meaning |
| --- | --- |
| `lock_unreadable` | the lock is missing or not valid JSON |
| `file_missing` | a file the lock lists is absent, the notice included |
| `digest_mismatch` | a file or the tree differs from the lock |
| `unexpected_file` | the skill holds a file the lock does not list |
| `glab_unavailable` | `update` cannot run `glab` |
| `skill_unknown` | `glab skills list` does not offer that name |
| `fetch_failed` | the fetch failed on every configured attempt |

- `verify` needs no `glab`, no network and no third-party package.
  `tools/ci_skills.py` imports PyYAML only inside `list` and `--yaml`, so CI
  can run `verify` before the dependency install.
- `update --dry-run` lists, per skill, the files that would be added,
  changed or removed, and writes nothing.
- A fetch heals before it blocks: `update` retries `attempts` times, waiting
  `backoff_seconds` between tries, then reports `fetch_failed` with each
  attempt's error.
- Only `update` calls `glab skills`. If that experimental command changes
  or disappears, `verify` and the vendored copies keep working.

## Update transaction

`update` changes several files at once, one tree per skill plus the lock:

1. Fetch every named skill into one staging directory beside `skills/`,
   with `glab skills install <name> --path <staging>`.
2. Check each staged tree: its frontmatter `name` equals its directory
   name, and its declared notice is present.
3. Write the new lock to a temporary file beside the current one.
4. For each skill, rename the current tree to a backup, then rename the
   staged tree into place.
5. Rename the temporary lock over the current lock.
6. Run `verify`. If any step fails, restore every backup and the previous
   lock, and report the failure; on success, delete the backups.

## Code placement

- The library is `tools/skillkit/`, not `tools/core/`. A Python process
  holds one module named `core`, and the installer and the live acceptance
  check bind it to the skill's `scripts/core/` to import `core.provenance`.
  A `tools/core/` package could not be imported beside it.
- `skillkit` imports `core.provenance` from the skill, as
  `tools/install_k8s_admin_diagnostics.py` already does, and computes the
  per-file hashes itself. Never the reverse: an installed skill ships
  without `tools/`, and editing `provenance.py` would change the skill
  digest.

## Steps

How we consume the skills that the installed `glab` ships:

1. Build `tools/skillkit/vendor.py` and the `verify` and `update` verbs of
   `tools/ci_skills.py`, with the tests below.
2. Declare `glab` and `glab-stack` in `skills/vendor.toml`, and add each
   notice from the upstream release's `LICENSE`.
3. Read `glab --version` and `glab skills list`.
4. Run `tools/ci_skills.py update glab glab-stack`, which performs the
   update transaction above.
5. Run `tools/ci_skills.py verify`; it must report `PASS`.
6. Add the `.markdownlint-cli2.yaml` ignores, the unconditional `verify`
   gate (GAL-GATES, G4) and `environment.yml`.
7. Open one pull request; the `validate` workflow must pass.

Steps 3 to 5 are also the refresh path: `update --dry-run` shows upstream
drift, `update` applies it, and the diff goes through a pull request.

## Gates

- **CI.** `ci_skills.py verify` runs unconditionally, before the dependency
  install (GAL-GATES, G4). A change to `.md` files only skips the gated
  workflow steps, and a vendored skill is almost all Markdown.
- **Markdown lint.** Vendored text stays byte-for-byte upstream. With the
  CI-pinned markdownlint-cli2 0.23.2, `glab` has 2 and `glab-stack` 30
  line-length findings (MD013). A committed `.markdownlint-cli2.yaml`
  lists `skills/glab/**` and `skills/glab-stack/**` under `ignores`; CI and
  local runs both read it.
- **Measured on the fetched copies.** No trailing whitespace, CRLF or tabs,
  so `git diff --check` passes; no gitleaks finding; no project-neutrality
  violation.
- **Environment.** A committed `environment.yml` (Python 3.11, with a pip
  section of `-r requirements.txt` so the pins stay in one file). The checks
  need `tomllib`, which Python 3.10 lacks.
- **Tests, run in CI.**
  - Flipping one vendored byte makes `verify` report `digest_mismatch`.
  - With no `glab`, `verify` still passes and `update` reports
    `glab_unavailable`.
  - The lock's `tree` equals `tree_digest`, and each `files` hash equals
    that file's SHA-256.
  - Declared tags, license and notice survive an `update`.
  - A failure at any transaction step leaves the previous trees and lock.
- **Receipt.** Nothing under `skills/k8s-admin-diagnostics/` changes, so
  the committed live receipt still applies until it expires on
  2026-11-01T22:35:26Z (`captured_at` plus `max_receipt_age_days`). After
  that, every pull request fails until a new receipt is committed.
